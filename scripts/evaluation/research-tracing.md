# Mem0 tracing, measurement, and evaluation research

Read-only review of current personal/main, 2026-10-05. No dependencies installed, AI requests made, or tracked files changed. CodeGraph consulted before code searching.

## Findings and implementation hooks

- Python `mem0/memory/telemetry.py:192` records PostHog usage events including provider classes and configuration; it is not a provider trace or authoritative benchmark record. TS `mem0-ts/src/oss/src/utils/telemetry.ts` samples hot-path events at 0.1 by default. Evaluation denominators must not depend on these sampled analytics.
- Python provider boundaries are `LLMBase.generate_response`, `EmbeddingBase.embed` and `embed_batch`, and `BaseReranker.rerank`. An implementation of an abstract base method is overridden by each provider: instrumenting only the base abstract method will NOT capture calls. Harness-installed instance proxies are a reversible initial approach; instrumentation factories are the later product integration point.
- Factories: `mem0/utils/factory.py` (`LlmFactory.create`, `EmbedderFactory.create`, `RerankerFactory.create`). TS interfaces: `mem0-ts/src/oss/src/llms/base.ts` has BOTH `generateResponse` and `generateChat`; cover both.
- OpenAI Python `mem0/llms/openai.py:141` calls SDK, parses response, then invokes `config.response_callback(self, response, params)` at :143. The callback exposes raw tokens/response but is success-only and occurs AFTER parsing. It cannot capture transport failures or parsing exceptions and doesn't provide start timestamp. Use wrapper timing + callback for an initial OpenAI-specific proof of concept, or SDK instrumentation for reliable raw capture.
- Ollama Python `mem0/llms/ollama.py:143` and TS `mem0-ts/src/oss/src/llms/ollama.ts` discard SDK usage and timing when converting raw completion to content/tool calls. Wrapping the returned content alone cannot reconstruct actual usage. Capture inside provider SDK call or wrap the SDK client's chat method. Ollama returns prompt/eval counts and total/load/prompt-eval/eval durations in nanoseconds; do not convert them as milliseconds. Distinguish missing usage from zero usage.
- TS Ollama `ensureModelExists` checks model list and may pull a missing model. A benchmark must preflight/install explicitly, distinguish initialization/model download from inference, and record warm/cold behavior. Constructor background initialization can race first request; establish readiness before measurement.
- Current downstream Python pipeline is V3 single-call additive extraction: `mem0/memory/main.py:1105` for sync and :2854 for async. Provider exceptions propagate as `LLMError`, but extraction JSON parse failures become empty extraction results around :1135 / :2881. A successful HTTP request and successful `add()` can therefore still be an ineffective model result. Add schema/semantic grading at the extraction phase; do not classify every empty extraction as a failure because some inputs contain no durable fact.
- Batch embeddings at :1146 / :2892 can fall back to individual embedding calls. Capture failed batch plus fallback calls, count all physical calls, but do not double-count tokens from a parent logical batch and its children. Track fallback/degraded results rather than marking eventual operation success as perfect reliability.
- Reranking around :1668 / :3428 can fail and fall back. Record fallback separately. Procedural generation at :2206 / :4007 and vision preprocessing need distinct purpose labels even if same LLM/provider instance is used.
- AsyncMemory uses `asyncio.to_thread`; ThreadPoolExecutor also appears at :1971. Verify context propagation with sync, async, thread pool, and failure cases. Explicit context copying is needed for ordinary executor submissions unless instrumentation provides it. Node needs AsyncLocalStorage/OTel context configured before instrumentation; test child span ancestry under Promise concurrency.
- Hosted MemoryClient is a remote API boundary: client spans measure network/end-to-end operation only. They cannot prove all internal hosted LLM calls are captured without service-side traces or vendor trace exports. State coverage explicitly.

## Proposed architecture

Use a backend-independent local evaluation ledger (JSONL plus manifest initially) as the authoritative experimental artifact. Optional OTel exporter sends traces to ONE chosen UI, Phoenix or Langfuse. This avoids forcing a service or SDK on every SDK user. Install SDK tracing/eval dependencies as optional extras, not core Python dependencies. No exporter must change results or block inference.

Each experiment creates a root case trace, with child Mem0 operation spans and phase spans (retrieval, extraction, embedding, rerank, persist, downstream answer). Provider call children use established SDK instrumentors where supported, otherwise small manual boundaries. HTTP child spans capture physical retry attempts if exposed. Maintain coverage manifest for all call sites including local in-process embeddings/rerankers and vector-store integrated embeddings, not just remote chat calls.

OTel GenAI conventions were moved/development status in reviewed docs: pin instrumentation and schema versions and normalize to a stable internal record. Do not assert vendor interoperability merely because fields have `gen_ai` prefixes. OpenInference and OTel GenAI are related but distinct schemas; pick and test an adapter for chosen UI.

## Stable internal record schema

Run manifest: schema_version, run_id, git SHA/dirty state, Python/Node and package versions, dataset/version/hash, case IDs and splits, prompt/tool/schema hashes, config hash, provider/runtime/endpoint classification, requested and actual model, exact model tag/digest/quantization, context length, temperature/top_p/token limit/seed, tokenizer version, embedding/reranker versions and dimensions, GPU/CPU/RAM/runtime versions, concurrency and rate policy, timeout/retry settings, state initialization/isolation, warmup/cold-cache status, clock and units, grader model/prompt/version, budget and stopping conditions. Sanitize configs so API keys and endpoint credentials never enter artifacts.

Case ledger: run_id, case_id, repetition, conversation/session/checkpoint, trace_id, operation ID, purpose, stage, start/end UTC, monotonic elapsed seconds, status, retry/fallback/timeout/cancel category, expected behavior and observed output artifact refs, scores, grader status, annotations, per-case persisted memory snapshot/state transition. Unique case namespace prevents cross-case memory contamination. Preserve case ordering for longitudinal tests and randomized paired model comparisons elsewhere.

Provider span/ledger: trace_id/span_id/parent_id, logical_call_id, physical_attempt_id when knowable, operation name (chat/embeddings/rerank), purpose, provider class, serving runtime, requested/response model, endpoint category, sanitized request params and prompt/tool hashes, request ID, finish reason, input/output/cache/reasoning token counts when available, usage_source (reported/estimated/unavailable), estimated cost with explicit price/version or null, embedding batch count/dimensions, start/end/duration, optional queue/TTFT/token timings only when measured, raw-response safe artifact ref, output parse/schema status, transport status, exception type and sanitized message, fallback/retry events. Mark attempt_count unknown if SDK hides retries; do not invent it. Separate workload spans from judge spans and report workload vs grader cost independently.

Map supported fields to `gen_ai.operation.name`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, server address where safe, and `error.type`. Mem0-specific fields belong under `mem0.eval.*` or documented internal namespaces. Store raw prompts/outputs in separately controlled artifacts rather than high-cardinality metric labels.

## What to measure

Compatibility/reliability: request success, parse/schema validity, required tool selection/argument correctness, truncation/refusal, semantic success, first-attempt success, eventual success, fallback frequency, completion coverage, retry amplification. Schema success is not fact accuracy.

Speed/load: end-to-end p50/p95/p99, stage/provider p50/p95, throughput (offered/completed), queue delay where measurable, timeout/error counts, memory/GPU use and server saturation, normalized output tokens/sec only when token duration is trustworthy. Client latency includes transport, scheduling, retries and processing; Ollama provider eval duration isolates generation. Non-streaming adapters do not expose TTFT; leave null. Separate cold/warm runs and exclude model downloading from inference measurements while reporting provisioning time.

Quality: extraction precision/recall against labeled durable facts; spurious memories; entity/date attribution; duplicate/superseded fact behavior; retrieval recall@k and ranking; relevant memory utilization; grounded downstream answer accuracy; privacy/user separation; stale-memory/update/delete retention. Use deterministic schema and rule graders first, reference matching when unambiguous, calibrated independent LLM judges and human adjudication for semantics. Never use the tested Qwen as its sole correctness judge.

Long-term: stateful session sequences with explicit checkpoints, intervening irrelevant chats, conflicting corrections, passage of time, large memory stores, restart/reload, update/delete, and retrieval after many writes. Verify persistence and state snapshots. A single prompt microbenchmark cannot answer long-term memory effectiveness.

Statistical reporting: repetitions and cases with denominator for every rate, uncertainty interval (Wilson for binomial success), paired comparisons and dataset strata. Failures and skipped cases are visible, never silently omitted. Separate functional pass rates from stress runs. Randomize/interleave model runs to reduce warmup/temperature/time confounds. Record seeds but do not promise perfect determinism.

Stress plan: synthetic, isolated memory namespaces; increasing concurrency and context/store size; bounded requests/token/runtime budget; ramp and steady-state separately; backpressure/timeout behavior; retry budgets and request cancellation. No arbitrary public service traffic. Monitor local runtime externally; client-only spans do not measure GPU saturation. Failure injection covers unavailable server, timeout, 429/5xx, malformed JSON, wrong tool args, partial embedding batches, NaN/shape errors, oversized contexts, missing model and reload.

## Feedback and privacy

Keep 100% of benchmark result rows even when trace export sampling is enabled; use 100% eval traces for diagnostics subject to explicit local budget. Flush exporters at CLI end and count lost spans/export failures. Redact before export/storage, use synthetic fixtures by default, omit credentials, hash identities, record retention and consent for real traces. Observability content capture can itself contain sensitive memory. Redaction may impair exact reproduction; preserve a secured local reference or note the limitation.

Selected failures become reviewed/versioned regression cases with provenance and expected outcomes; quarantine judge-uncertain examples; keep holdout set separate from tuned examples. Join user annotations and automated scores by trace/case IDs. Learning means experiment feedback and regression datasets here, not automatic fine-tuning or changing production prompts.

## Tool choice and primary sources

- OpenTelemetry GenAI conventions: https://opentelemetry.io/docs/specs/semconv/gen-ai/ and https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/ — reviewed pages indicate migration/development/deprecation, so pin actual schema.
- Phoenix tracing https://arize.com/docs/phoenix/tracing/llm-traces — OTLP ingestion, provider/framework instrumentation, Python/TS coverage, annotations and operational metrics. Existing SDK instrumentor coverage must be verified against the particular Mem0 providers; local inference requires manual spans if no matching instrumentor.
- Phoenix source https://github.com/Arize-ai/phoenix and TS experiment API https://arize-ai.github.io/phoenix/functions/_arizeai_phoenix-client.experiments_runExperiment.runExperiment.html — experiment/evaluator infrastructure, not a Mem0-specific correctness suite. Phoenix is a strong choice for local Python-first experimentation; self-host deployment requirements need separate validation.
- Langfuse tracing https://langfuse.com/docs/observability/get-started — SDK/manual/OTel and OpenAI wrapper. https://langfuse.com/docs/observability/sdk/advanced-features — thread/process guidance.
- Langfuse datasets https://langfuse.com/docs/evaluation/experiments/datasets — linked dataset runs and experiments. https://langfuse.com/docs/observability/features/masking — masking hook for raw OTel attributes before export. Langfuse is a strong alternative for Python+TS prompt/version/feedback workflows; don't run two backends initially.
- Ollama raw timing and tokens https://docs.ollama.com/api/chat — prompt/eval token counts and nanosecond durations, optional structured format; measure capabilities per exact model/runtime rather than assuming Qwen tool/JSON support.

Recommendation: start with local ledger + harness wrappers that preserve existing provider contracts; add raw SDK usage collection and phase/schema grading. Export to Phoenix optionally for Python experiments, or Langfuse if prompt management across TS/Python is the priority. Reuse an external benchmark suite for stateful quality, but add project-specific extraction/tool/schema/embedding/rerank/load tests because external end-to-end QA benchmarks will not localize every internal call failure.
